Written for whoever runs the deploy and whoever reads `/health/stages` afterwards.

Line: `84d8afa` (0.3.0) -> `c9186b1` -> `fe8ea83` (0.3.1) -> `88d18b6` -> `2e2fa41`
-> `7a5a69a` -> `0f3fe6d` -> `9763cf9` -> `824b8d2`. `release-0.3.2` **contains**

which was never an ancestor of `main`, so a deploy from a `main` checkout taken
before 2026-10-11 silently regressed production to 0.3.0. Both release branches
and the two forward-merges are now on `origin` (`main` @ `a88ad6f`), so that

`/health/stages` semantics: healthy means "ran at least once in this process AND
recorded no fault". Never-ran reads **false** (errs toward alarm). A fault always
wins. Cumulative since process start. A stage this build cannot observe gets **no
boolean** and is named in `not_observable`, so a consumer gets a `KeyError`
instead of a wrong answer.

## Operational caveats

- **`/health/stages` is reachable only from INSIDE the cluster in 0.3.2.**
  The ingress routes `/` -> ui and `/api` -> backend, and the route is
  registered at `/health/stages`, not `/api/health/stages` -- so from outside,
  the whole `/health*` tree is served the frontend SPA. Measured 2026-10-18:
  `curl http://test.chart-example.local/health` returns `200` with
  `<!doctype html>`. **A monitor consuming this endpoint must run in-cluster**
  (`kubectl exec`, or a port-forward). `/health` itself is unaffected in
  practice only because the kubelet probe in `api-deployment.yaml` addresses
  the pod directly and never traverses the ingress. This is accepted for
  0.3.2 rather than fixed: moving a liveness-adjacent route in a patch release
  is the larger risk. **0.3.3 adds `/api/health/stages` additively, keeping
  the old path**, alongside the D-003 attempt counter.

- **`envFrom` is read at container start.** `GYA_DEBUG_STAGES` is not a live
  toggle: a configmap edit needs a rollout restart, despite the per-call read
  in the code. (The same will apply to `GILL_STRUCTURED_ANSWER` -- but that
  flag ships with `ac71b00`, which is **not** in 0.3.2 and is carried only by
  the `body-path` branches. Setting it against a 0.3.2 image sets a variable
  no code reads.)
- `values-test.yaml` sets `GYA_DEBUG_STAGES: "1"` for gya-test; `values.yaml`
  sets `"0"` explicitly for production. The eval lane and
  `evals/zone3_eval_replay.py` (a daily monitor) both need the flag on their
  target, or they abort naming it.

## The retry bound is DECLARED, not OBSERVED

This is the caveat to carry into reading `/health/stages`. The policy is
asserted in `baml_src/main.baml` and in the inlined copy the runtime actually
parses, so the retry *happens*. But **no attempt counter reaches
`stage_health`** in this release: a call that burned all four attempts and then
failed is indistinguishable from one that failed on its first try. So
`/health/stages` **cannot tell flaky transport from broken transport**, and
`expansion: false` after a transport fault says nothing about how hard the
backend tried. The counter is a 0.3.3 item — **D-003** — not an oversight to
discover during an incident.

What the retry also does not cover: it retries *transport* faults only. A model
that answers wrongly, slowly, or with an unparseable body is untouched, and four
attempts add ~1.4s of latency on the one request in 67 that needs them.

## What this release does NOT solve

- **Nothing in 0.3.2 had been exercised against a deployed backend as of the
  cut.** The 403, the projection and the retry were unit assertions and source
  probes in this repo — not one request to a pod. The smoke list was
  `/health/stages`, a nested-quote citation verifying, and debug 403/200 by
  flag.

  **Since run: 2026-10-18 on gya-test**, against
  `backend@sha256:ac37c84fed...66d0c7d8e` (built from `a88ad6f`). All three
  items passed; the record, every command and the chart-drift note are in
  `docs/audits/SMOKE_BLOCKED_gya_test_deployment_state_laneA_20261011.md`.
  Two caveats carry forward: the nested-quote item was verified against the
  **deployed code path** (the regex in the image, and the three recorded
  instances through the deployed pairing function, gated in both directions)
  because neither live generation happened to produce the shape -- it was ~8%
  of recorded answers; and four requests is not a scored run, so the gate's
  pass rate is still unmeasured on that pod.
- The derived debug-consumer probe reads `evals/` only. A consumer one directory
  over, or one building the payload dynamically, is invisible to it — the exact
  shape of the miss it was written for.
- The hardcoded `192.168.1.179`/`.188` base URLs on the `Ollama` and `OllamaGPT`
  clients in `main.baml` are untouched on purpose: pipeline endpoint-safety work,
  not a release change, and neither client is on a backend path.
- When expansion fails, the product still tells the user nothing.
