# Release 0.3.4 — scope

**Status: scope only. Nothing here is implemented, and nothing here is decided
except where it says so.** This file exists because 0.3.4 items were being
carried in conversation with no home in the repo; a scoped item with no file is

## Scoped

### 1. A `.dockerignore`, so a docs commit can never change an image

**Ruled 2026-11-15.** The api image builds with `context: .` and a root
`Dockerfile` whose `COPY . /app/` takes the whole repo, and there is no
`.dockerignore`. So `docs/`, `evals/`, `charts/` and every audit file are inside
the api build context. The 0.3.3 forward-merge brought three `docs/` files, and
they are in the context of any api rebuild.

Nothing was deployed wrongly by this: both 0.3.3 images are referenced **by
digest**, nothing in the 0.3.3 work rebuilds, and the build workflow triggers only
on push to `main` and on tags — never on a release branch. The pinned digests
`2fce1e34` (api) and `f386254e` (ui) are unaffected and remain the gate-scored
artefacts.

What is wrong is the *proof*: ruling 13 item 2 asked for `git diff` across the
merge on `backend/` and the frontend context to be empty, and it was — but that
surface is narrower than the real context, so the test as stated would pass for a
change that *did* alter a rebuild.

Acceptance:
- `.dockerignore` at the repo root excluding at least `docs/`, `.git/`,
  `charts/`, `evals/baselines/`, `**/__pycache__/`, and the lane trees.
- A check that the api image's effective context contains no `docs/` path — built
  from `docker build --no-cache` output or from the context tar, not from reading
  the `.dockerignore` file. A file-scoped assertion cannot see what the builder
  actually sends; that is the same lesson as the chart tests in `4179350`.
- Before and after image digests recorded. A `.dockerignore` **changes the build
  context**, so it can change a digest; that must be a measured statement, not an
  assumption.

### 2. A CI check that a `release-*` branch is not behind `main`

From `RELEASE_PROCESS.md`'s own "does NOT solve": step 0 is a manual command, and
a manual command is what 0.3.3 skipped. `git log --oneline release-X.Y.Z..main`
non-empty should fail the branch.

### 3. `strategy` in the drift gate's compared keys

`deploymentUpdate.type` was the one of 0.3.3's three faults that produced no gate
line at all. `drift_hash.py` lives in `~/.gya/` and is Chris's; this is a request,
not a change made here.

## Named, not decided

These four came out of the 0.3.3 cycle and each needs a ruling. They are listed
so they are findable, not because any of them is settled.

- **D-003 (retry bound declared, not observed) — carry or hold.** Whether 0.3.4
  carries the fix or the defect stays open across the release.
- **`kjv_fast_lookup.json`** — which keys the API needs, and whether the eval host
  that produced the 0.3.3 numbers had the file at all. The second half decides
  whether those numbers are about the shipped lookup path.
- **`checksum/secret` alongside `checksum/config`** — whether a secret change
  should restart the api pod the way a config change now does (D-007).
- **`quote_repairs` in the API response** — whether the repair record is part of
  the contract or stays internal.
