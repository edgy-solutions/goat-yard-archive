# Release 0.3.4 — scope

**Status: scope only. Nothing here is implemented, and nothing here is decided
except where it says so.** This file exists because 0.3.4 items were being
carried in conversation with no home in the repo; a scoped item with no file is
a note, and this release cycle has already shown what a note is worth.

## Scoped

### 1. A `.dockerignore`, so a docs commit can never change an image

**Ruled 2026-11-15.** The api image builds with `context: .` and a root
`Dockerfile` whose `COPY . /app/` takes the whole repo, and there is no
`.dockerignore`. So `docs/`, `evals/`, `charts/` and every audit file are inside
the api build context. The 0.3.3 forward-merge brought three `docs/` files, and
they are in the context of any api rebuild.

Nothing was deployed wrongly by this: both 0.3.3 images are referenced **by
digest**, nothing in the 0.3.3 work rebuilds, and the build workflow triggers only
on push to `main` and on tags — never on a release branch. The pinned digests
`2fce1e34` (api) and `f386254e` (ui) are unaffected and remain the gate-scored
artefacts.

What is wrong is the *proof*: ruling 13 item 2 asked for `git diff` across the
merge on `backend/` and the frontend context to be empty, and it was — but that
surface is narrower than the real context, so the test as stated would pass for a
change that *did* alter a rebuild.

Acceptance:
- `.dockerignore` at the repo root excluding at least `docs/`, `.git/`,
  `charts/`, `evals/baselines/`, `**/__pycache__/`, and the lane trees.
- A check that the api image's effective context contains no `docs/` path — built
  from `docker build --no-cache` output or from the context tar, not from reading
  the `.dockerignore` file. A file-scoped assertion cannot see what the builder
  actually sends; that is the same lesson as the chart tests in `4179350`.
- Before and after image digests recorded. A `.dockerignore` **changes the build
  context**, so it can change a digest; that must be a measured statement, not an
  assumption.

### 4. The scan gallery's page label can name a page the citation does not

Filed in the defect register as
[D-008](../defects/D-008-viewer-opens-on-the-page-before-the-citation.md).

**Found 2026-11-15**, from Chris's observation: the evidence panel read
`Vol 1, p. 106` for Genesis 2:15 beside a viewer labelled page **105**. Read
from the code, there are **two** mechanisms that produce exactly that pairing,
and which one fired is decided by one thing Chris can answer in a glance:
**was a highlight rectangle drawn?**

The gallery always renders three pages, `[cited-1, cited, cited+1]`
(`App.tsx` `getGalleryPages`: `startPage = Math.max(1, minPage - 1)`), so the
**first page in the DOM is always the page before the cited one**.

- **If a highlight was drawn — a LABEL defect.** `ScanGallery`'s auto-scroll
  centres the *highlight boxes* in the viewport, not the top of the cited page,
  so with a box near the top of 106 a large part of 105 is on screen. The label
  is `visiblePage`, chosen by `IntersectionObserver` as the page with the
  highest `intersectionRatio`, and the hysteresis then **locks it**: a rival
  page must beat the current one by `0.25` *absolute ratio*
  (`maxRatio - currentRatio > 0.25`). `intersectionRatio` is the fraction of
  the **element** visible, and a page element is taller than the viewport, so
  the maximum ratio any page can attain is `viewportH / pageH` — often under
  0.5. The threshold is in element-fraction; the question is share-of-viewport.
  **A control scored in different units from the thing it gates has gated
  nothing**, and once 105 is current, 106 can lose while holding the highlight.
  The viewer is on the cited content; the caption is not.
- **If no highlight was drawn — a NAVIGATION defect.** With
  `pages.filter(p => p.boxes.length > 0)` empty, or the cited page's image not
  loaded, the auto-scroll effect **returns before scrolling**. The container
  stays at `scrollTop 0`, which is page `cited-1`. The viewer then really does
  open on the page before the citation.

**2026-11-15, from Chris's screenshot: the viewer showed page 105 (Gen 2:10-12)
with NO highlight rectangle, while the panel cited Gen 2:15.** That is the
second branch — the **navigation** defect: the viewer opens on the page before
the citation, and the label is telling the truth about where the viewer is. The
label mechanism above is still a defect (the unit mismatch is real, and it
fires once a highlight exists), but it is not what this screenshot shows.
Chris will confirm by scrolling — if 106 carries a highlight that was simply
off-screen, both branches are live at once.

Acceptance:
- The caption must name what it is computed from, or fall back to the cited
  page when the most-visible page is not the page carrying the highlight. One
  record must not carry a true and a false statement about one citation.
- The hysteresis threshold must be expressed in the same unit as the quantity
  it compares — share of the viewport, not fraction of the element.
- The no-boxes path must scroll to the cited page rather than return. A
  citation with no coordinates is still a citation; `scrollTop 0` is a page the
  system never claimed.
- A fixture for each branch, asserting the caption against the cited page.

### 5. Every user-visible page number is a FILE page, and users must see the PRINTED page

Filed in the defect register as
[D-009](../defects/D-009-every-user-visible-page-number-is-the-scan-file-page.md).

**Ruled by Chris, 2026-11-15: users see the printed page of the BSB volume,
never the scan-file page. The scan number is not shown to users.** Internals
keep file pages exactly as now; only the rendering changes.

Where the file page is born: `gill_search.py:343` builds
`[Vol {vol}, p. {page}]` from `page_number`, which `ingest.py:1030` writes from
`parse_page_info`'s parse of the **filename** (`page106_image1.png`). For
volume 1 the printed page is `file - 88`, so the panel's `p. 106` is printed
page **18**, and the viewer badge's `PAGE 105` is printed **17**.

This is why the scan URL resolves — the citation string and
`/scans/vol1_page106_image1.png` come from the same field in the same frame, so
they cannot disagree — and why the number is not citable: a reader who opens
Gill vol. 1 at p. 106 does not find Genesis 2:15.

#### Every place a page number reaches a user

Read from the code, 2026-11-15. All of these render the file page today:

| where | code | shows |
|---|---|---|
| evidence panel citation | `App.tsx:799` ← `ev.citation` ← `gill_search.py:343` | `Vol 1, p. 106` |
| viewer badge | `App.tsx:949` | `Vol. 1 — Page 105` |
| gallery per-scan label | `ScanGallery.tsx:101` | `Page 105` |
| scan `alt` text | `ScanGallery.tsx:110` | `Page 105` — screen readers |
| hover titles | `App.tsx:692-693`, `App.tsx:761` | `View Source: [Vol 1, p. 106]` |
| citations array | `main.py:1108` → `App.tsx:821` | the same strings |
| dev fixture | `frontend/src/mock_data.ts:7` | `[Vol 1, p. 287]` |

And one channel that is **not** a render, and that rendering cannot fix:

- **The answer LM is handed the file page inside its context.**
  `bot.py:1016-1020` writes `citation_tag` into `formatted_context`, and the
  `GillSignature` input field says the context is *"tagged with Sentence IDs
  and [Vol, Page] citations"* (`bot.py:984`). The prompt tells the model to
  cite with inline SIDs, not `p.` strings, so in practice the prose does not
  carry page numbers — but **the number is in the model's input**, and any draw
  that echoes it produces a file page inside generated prose, downstream of
  every render fix. Changing that tag is a **prompt-surface** change and is
  gated by the standing rule (a prompt edit can move the verbatim boundary and
  regress `verified`); so either the tag carries the printed page under the
  same gate, or a check asserts the answer prose contains no `p. <n>` string.
  **Named, not decided here.**

#### The mapping is per volume, and it is not in this repo

Searched 2026-11-15: **no `printed_page`, `page_offset`, `PAGE_OFFSET` or page
`-88` exists anywhere in the repository** — not in `backend/`, not in
`pipeline/scripts/`, not in the chart. Volume 1's offset of 88 is a lane fact
carried in notes and handoffs. So there is nothing to generalize from and
nothing to copy: the per-volume mapping has to be **created** by this item, and
the other served volume's offset does not exist yet.

How the other volume's offset must come about — **derived by a stated rule, not
pinned as a number somebody remembered**:

1. Read the printed number in the **running head** of a sample of scans for
   that volume, recorded as readings with the file page beside each.
2. Solve for the offset, and require it to be **constant across the sample**.
   A sample that yields two offsets means the volume has a discontinuity (an
   inserted plate, a numbering restart) and a single integer is the wrong
   model — say so rather than averaging.
3. Record the offset with the volume, the sample it was derived from, and the
   date. A constant with no derivation beside it is unauditable.

**Front matter needs a third state, not a number.** Pages whose printed number
is roman, or absent, have no arabic printed page, and no integer offset covers
them: `file 1 - 88` is negative. The mapping is therefore a **function with a
declared domain**, and a page outside that domain renders as what it is — the
roman numeral, or front matter with no number — **never a clamped 1, never a
negative, never a silently substituted file page**. A system with no "this page
has no printed number" channel turns an honest gap into a fabricated citation.

#### Acceptance

- Every row of the table above renders the printed page, or does not render a
  page number at all. One record may not carry a true and a false statement
  about one page.
- The response carries both numbers under **distinct names** (`page` stays the
  file page for the scan lookup; the printed page is its own field). No
  consumer infers one from the other by arithmetic at the call site.
- The mapping lives in **one named place, keyed by volume**, with its
  derivation sample and date beside it, and returns a typed "no printed number"
  for front matter rather than an integer.
- **Born-tests, per volume**: a sample of pages whose expected printed number is
  a *recorded reading of the running head*, not a value computed by the mapping
  under test — a test that derives its expectation from the code it checks
  proves nothing. Assert the **count** of sampled pages too, so a sample that
  silently shrinks reads as a failure rather than as silence. At least one
  front-matter page per volume, asserting the no-number state.
- The scan URL still resolves from the file page after the split, and a test
  says so.
- The dev fixture is updated with it, or it will teach the next reader the old
  contract.

Filed alongside item 4 (the viewer opening one page early): both are
pre-existing, both are user-visible, and a user looking at the Genesis 2:15
panel today meets both at once.

### 6. Pin `wrangler`, and put the Worker deploy in CI

`wrangler.jsonc` is at the repo root with no root `package.json`, so `npx
wrangler` resolves whatever is current and the config's own `$schema` path
(`node_modules/wrangler/config-schema.json`) never exists. No workflow deploys
the Worker. Three releases shipped past a three-month-old public bundle because
the deploy is a hand-run command with nothing watching it
(`RELEASE_PROCESS.md` § Step 5).

Acceptance: a pinned wrangler version; a workflow that deploys on a tag or
records that it did not; and the public build identifier recorded per release
whether or not the deploy is automated.

**The 0.3.3 redeploy rides here.** The public bundle already contains every
frontend change through `release-0.3.3` (measured: `assets/index-fx2QcAsD.js`
carries the post-`e0bf95e` scan URL), so the redeploy is **hygiene, not a fix**,
and it is scheduled with 0.3.4 rather than run against 0.3.3. Items 4 and 5
above are the first changes that will actually need it.

### 7. The witness prints the context SID count, not the set

**Found 2026-11-15**, from the x5 witness on `predestination_001`: five draws,
five distinct cited-SID sets, `context_sids` 33/37/36/33/33. Two draws report
the same **count**, cite differently, and cannot be told apart — because
`evals/accept_0_3_3.py` computes the context as a `set` and reports only
`len()`. Equal counts are not equal sets, so the run cannot separate *the
retrieval moved* from *the answer LM chose differently from the same context*.

This is the cheap half of a decomposition whose expensive half needs
`GYA_DEBUG_STAGES=1` (`retrieval_sids_set` and `embedding_hash` already exist in
`main.py:742-760`) and therefore cannot run on prod. A stable hash of the sorted
SID set, printed per draw, separates the two on prod out of the ordinary
response body.

Acceptance: each draw prints a digest of its sorted context SID set; a run where
the digests are equal and the citations are not is reported as **generation
variation, observed**; a run where the digests differ is reported as retrieval
variation. Neither is asserted as a pass or a fail — no release claims
answer-level determinism, and this item does not create one. Full reasoning in
[`docs/audits/X5_WITNESS_VARIATION_laneA1_20261115.md`](../audits/X5_WITNESS_VARIATION_laneA1_20261115.md).
